# Pre-flight: gh3245_referral_code_v4_gate

Issue #3245 (vehicle per Ben's ruling, #3243 comment 6563033722), refs #3243, #3244, PR #3279. Tier 3B. Needs REVIEW + LEGAL-READ + R-177 pair; R-097 notice and Dustin's word before any apply.

## Page coupling: read this before applying
The function now returns `unique_code: null` and `v4_acceptance_required: true` to a customer who has not accepted v4 (it does not raise, because a raise rolls back
the row insert and `accept_partner_agreement_v4()` then fails with `no_partner_record`). Both refer pages currently run get-or-create FIRST and treat a null code as failure:
- `refer-a-friend.html` `acceptAgreementV4()`: `if (!userReferralCode) await fetchOrCreateReferralCode(); if (!userReferralCode) throw new Error('no referral code');`
- `react-app/app/refer/utils.ts` `acceptAgreementAndIssueLink()`: `const code = await deps.getOrCreateCode(); if (!code) throw new Error('no referral code');`
Applying this migration alone therefore breaks first-time acceptance (and acceptance by existing unaccepted customers). The pages must first change to: get-or-create (to create the row; null code
is expected) -> `accept_partner_agreement_v4()` -> get-or-create again (returns the code). That is a logic change, not new wording; the pinned call-order tests (`tests/gh3239-partner-agreement-v4.mjs`,
`react-app/app/refer/__tests__/refer.test.ts`) change with it. Not part of this PR. On the initial load, PR #3327 (head `7f76f28d`) reads "accepted" the way this function does (`partner_v4_accepted_at`: the v4 key needs a non-empty `accepted_at`, the version column needs `partner_agreement_accepted_at`; the static page reads the customer row only) and, if the server still answers `v4_acceptance_required`, shows the existing accept-first gate on both pages.

## Behaviour
| caller | result |
|---|---|
| customer row accepted v4-2026-10 (per `partner_v4_accepted_at`) | the code, exactly as before |
| customer row not accepted (or only an older version), existing row | `unique_code` null, `v4_acceptance_required` true |
| no customer row yet | row created (code generated by trigger, not returned), same null result |
| no session / no email | `not_authenticated` / `missing_email`, unchanged |

Note: customers who already hold a pre-v4 code and share it keep a working `/ref/<code>` link (nothing here touches link resolution); they just are not shown it again until they accept.
