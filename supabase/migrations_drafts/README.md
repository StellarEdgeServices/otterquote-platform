# supabase/migrations_drafts/

**Directory rule (gh-1438).** This directory is for SQL that has been written but is **not** applied to production. Nothing here is run by any automation: the documented deploy chain applies what is in `supabase/migrations/` (merge to main, then the Supabase migration step described in `CLAUDE.md`; no workflow in `.github/workflows/` runs migrations today, and the #1438 thread records migrations applied by hand; `supabase/migrations/README.md` also documents that the Supabase CLI replays that directory forward onto every fresh branch), and `supabase/migrations_drafts/` is not on that path. An unapplied draft reaches production only through the Tier 3B path (migration-author, review, R-097 notice, a recorded apply), never ad hoc. Once a set is applied to production, its forward file must be filed in `supabase/migrations/` under its real ledger version (`<14-digit version>_<name>.sql`, the version in `supabase_migrations.schema_migrations`) and its rollback and pre-flight in `supabase/migrations_rollbacks/` (some unapplied sets already keep their rollback and pre-flight there, see the table), so the repo history describes the database; a migration applied outside the ledger (SQL editor, MCP `execute_sql`) is filed in `supabase/migrations_applied_manually/` instead. Do not run a file from this directory outside that path; for an applied set, the filed copy is the record and the draft must not be run again. Every file here carries a `STATUS (gh-1438, ...)` header (`APPLIED`, `NOT APPLIED` or `UNVERIFIED`) naming its evidence and any repo copy; the header's `as of` stamp is when the header was written; the measurement date is the one its EVIDENCE line cites. It is not a live check. `python3 scripts/migrations-drafts-status-check.py` checks that every file has the header (presence only, not truth), and is not wired into required CI. See `supabase/migrations/MIGRATIONS-RECONCILIATION-1438.md` for the reconciliation this table summarises.

Some files here are read by other code and must not be moved without updating the reader: `supabase/functions/docusign-webhook/price-verify.test.ts` reads `gh1314_persist_signed_price.sql` (a Deno test on CI, read allowlist in `.github/workflows/e2e-tests.yml`), and `sql/schema-pending.json` names the same file as the migration that closes five pending `claims` columns.
