## What the amendment means, and the narrowest reading built
"No bid opens on an unread estimate; no identity in a summary" are the two conditions of the bid-release trigger Ben cut out of #2569 (`claims_guard_bid_release`, heads `2e130cde` / `c60b216f`, which failed REVIEW 6024856617 on five findings). So:
- **"a bid opens"** = the claim opens for bidding: `claims.ready_for_bids` false/NULL to true (the two submit paths are `dashboard.html` `submitForBids` and `react-app/app/(homeowner)/dashboard/actions.ts` `submitForBids`). It is NOT a contractor creating a quote, and it is NOT a contractor "opening" an estimate: no table records a contractor reading an estimate (grep for estimate_viewed / acknowledged: 0 hits), and since #2569 a bidder can read no raw upload.
- **"unread estimate"** = the claim carries an uploaded estimate (`estimate_filename` set or `has_estimate`) and it has not been read into the summary a bidder prices from: `loss_sheet_parsed_at` NULL, or `parsed_line_items` not an object with a non-empty `sections` array or a `summary.rcv`.
- **"identity in a summary"** = `parsed_line_items` or `contractor_scope_summary` (the two summary columns `bidder_claim_summary` returns) repeats the owner's name (`claims.homeowner_name` or `profiles.full_name`), the street line of `property_address`, or `claim_number`. Matching rules are in the forward file header.

## Changed after REVIEW 6276857463 (Marty's rulings, Tier A)
- **Blocker 1, a file the platform cannot read.** Both clients accept PDF, JPG, PNG and Word estimates; `parse-loss-sheet` sent every file to the provider as `application/pdf`, so 4 of the 5 accepted types never parsed (real claim `4595b6f0`, a .jpg, was refused for good). Now: (a) `parse-loss-sheet` decides the type from the file's bytes (`estimate-kind.ts`): PDF as a `document` block, JPEG/PNG as an `image` block with their real media type (the provider's messages API accepts images; 5 MB per image, measured on the base64, so the raw cap is 3,932,160 bytes). (b) For anything else (Word, HEIC, an oversize image, an empty file) it writes `claims.loss_sheet_parse_status = 'unsupported'` and a `platform_alerts_log` row (`alert_type loss_sheet_unsupported_type`, the operator surface) and returns 200 `{unsupported:true}`. Condition 1 lets such a claim open; there is no parsed summary, so a bidder sees none of the estimate's fields. A client cannot write the column (42501), or it could skip condition 1; the same refusal covers the other parse results (`loss_sheet_parsed_at`, `parsed_line_items`, `contractor_scope_summary`), which `authenticated` could otherwise type to forge a "read" estimate (review 6277230163 F1/F1b; no client code writes them, grep of every .html, .ts, .tsx). Re-trigger a parse: POST `parse-loss-sheet` with the service-role bearer and `{claim_id, storage_path}` (its existing service-role path: no ownership or rate-limit check); there is no new admin-JWT path. **Q6 for Ben (default built): a claim whose estimate the parser cannot read opens for bids without an estimate summary, plus an operator alert.**
- **Blocker 2, React.** `actions.ts` returns `error: undefined` for a guard refusal, so `Checklist.tsx` shows its existing generic line; the database text is never shown. Ordinary database errors pass through as before.
- **Required 3, replaced estimate.** New trigger `claims_guard_a0_parse_state` (BEFORE INSERT OR UPDATE OF estimate_filename, loss_sheet_parse_status): a change of `estimate_filename` clears `loss_sheet_parsed_at`, `parsed_line_items`, `contractor_scope_summary` and `loss_sheet_parse_status` (each unless the same statement set it). The old parse can no longer satisfy condition 1 (probe X2 is a must-refuse row in the behaviour run and the proof). Effect on an OPEN claim: a replaced estimate shows no summary to bidders until the new file is parsed (the upload already fires the parse). The stale-summary race (an in-flight parse of the OLD file finishing after a replacement) is closed in `parse-loss-sheet`: both its parse write and its `unsupported` mark carry `.eq("estimate_filename", storage_path)`, and a zero-row result for that reason returns 200 `{stale:true}` instead of an error (all three callers, dashboard.html, actions.ts and trade-selector, store the same path they pass). Consequence for the operator re-trigger: pass the claim's CURRENT `estimate_filename` as `storage_path`, or the call is discarded as stale.

## How it avoids the five findings that sank the cut trigger (REVIEW 6024856617)
| finding | here |
|---|---|
| 1 submit within about a minute of upload is refused | the same refusal exists (it is the condition), but the submit paths now WAIT silently for `loss_sheet_parsed_at` (up to 90 s, polling 3 s) before writing, with no new text; if the read never lands the database decides and the existing generic line shows |
| 2 name and claim-number checks compare empty columns | names come from `claims.homeowner_name` AND `profiles.full_name` (31 of 34 claims have a profile name; `homeowner_name` 9; `claim_number` 0) |
| 3 walk-around on an already open claim | identity is re-checked whenever the summary or the identity columns change on an open claim (including service_role writes by parse-loss-sheet) |
| 4 an empty parse passes | NULL-safe predicate; `{}`, `{"error":...}`, `sections: []` without rcv are all "unread" |
| 5 substring false positives and misses | whole-word, folded matching; numbers are never matched as names or streets; claim numbers need 6+ characters with a digit |
