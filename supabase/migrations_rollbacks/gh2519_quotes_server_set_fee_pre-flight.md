# Pre-flight: gh2519_quotes_server_set_fee (Tier 3B, DRAFT)

NOT APPLIED. Refs #2519, ruling 6049007305 (CTO RUN 62). It is not the R-134 fast path: it rewrites what a live bid path stores, so it applies only after review, the R-177 signature and an R-097 24-hour notice. The price-and-fee lock on a selected bid (D-369) is a separate draft, `gh2564_quotes_selected_price_lock.sql`.

No fee, rate, basis or price rule is chosen here. Every number comes from `public.platform_fee_config`, which on production holds one row: `fee_pct 5.00`, `fee_basis bid_amount`, state and trade NULL, effective 2026-05-06 (SELECT, 2026-10-08).

## What it does
For client callers only (`current_user` is `anon`/`authenticated`, JWT role is not `service_role`, caller is not an admin). `service_role` (every Edge Function) and admins are untouched, as are owner-level `SECURITY DEFINER` functions, with one exception: `accept_bid()` is re-created (item 6) and one partial unique index is added (item 4c).

1. **New bid (INSERT).** `platform_fee_pct`, `fee_percentage` and `platform_fee_basis` are written from the fee config row for the bid's contractor and claim; `fee_amount` is `round(rate / 100 * total_price, 2)`, the formula `normalize_quotes_fee_amount()` already applies. Whatever the browser sent in the four fields is overwritten, not refused. With no config row the bid is refused (`P0001`): the function holds no fallback rate.
2. **The bid's own contractor's UPDATE.** The three rate fields keep their stored values and `fee_amount` is recomputed from the new `total_price`. A legacy row with no `platform_fee_pct` keeps it NULL and its `fee_amount` is computed from `fee_percentage`.
3. **Column allow-list on UPDATE.** Claim owner: `status` (to `selected` or `declined`, as today) and `homeowner_signed_at`. The bid's contractor: `total_price`, the four fee fields (server-set), `fee_accepted_at`, `scope_summary`, `notes`, `decking_price_per_sheet`, `full_redeck_price`, `supplement_acknowledged`, `trade_type`, `value_adds`, `per_trade_breakdown`, `auto_renew`, `warranty_option_id`, `warranty_snapshot`, `workmanship_warranty_years`, `contractor_signed_at`. Both: `updated_at`. Any other changed column is refused 42501 and the message names it. On INSERT, `is_test`, `payment_intent_id`, `payment_method_id`, `payment_method_type`, `card_fee_cents`, `docusign_envelope_id`, `cancelled_at`, `cancellation_reason`, `expires_at`, `expired_at`, `warranty_document_url` and `warranty_uploaded_at` must be at their defaults.
4. **One selected bid per claim, three parts (re-review 6051423781 findings 1 and 3).**
   - **(a) The definition.** A bid blocks another from being selected only when it is *live*: `status` selected, `bid_status` active, and its contractor is the claim's current selected contractor (`claims.selected_contractor_id`). Setting a bid to `selected` is refused 42501 only when the claim has a live selected bid. A bid that was switched away from (`switch-contractor` resets the claim to `bidding` with no selected contractor and leaves the old bid `selected`) or rescinded (`bid_status` no longer active) does not block a new award.
   - **(b) The clean-up.** When a client or `accept_bid()` selects a bid, any other bid left `selected` and active that is not live is set to `declined` in the same statement.
   - **(c) The index.** `quotes_one_selected_bid_per_claim`, a partial unique index on `quotes (claim_id) WHERE status = 'selected' AND bid_status = 'active'`, closes every other route: two simultaneous direct UPDATEs, a direct UPDATE beside `accept_bid()`, `service_role`, the SQL editor.
   - **The two exits are not changed here, and their defects are these.** `switch-contractor` (step 6) writes `quotes.status = 'cancelled'`, which `quotes_status_check` (draft, submitted, selected, declined, expired) refuses; the function logs "Non-fatal" and goes on to reset the claim, so the old bid stays `selected`. `rescind-bid` writes `quotes.bid_status = 'rescinded'`, which `quotes_bid_status_check` (active, expired, superseded, cancelled) refuses, so the function answers 500 "Failed to rescind bid" and today no bid can be rescinded; even once repaired it leaves `status` selected. Both are deployed Edge Functions and are not touched by this PR. The definition in (a) and the clean-up in (b) are what keep a claim from being stranded after either exit (proof W3, RB2, RB3).
5. **`apply_referral_commission()`** reads the bid of `claims.selected_contractor_id` (one added predicate, `AND contractor_id = NEW.selected_contractor_id`); the rest of the function is byte for byte the live body.
6. **`accept_bid()` refuses a second LIVE selected bid** (review 6050036561 finding B1; CEO ruling 6050104316). The function is `SECURITY DEFINER`, so the guard in item 4 never sees its caller as a client and could not refuse. The live body (prosrc md5 `07ae60dd`) is kept and these are added, each marked `gh-2519`: the claim row is locked FIRST with `FOR NO KEY UPDATE`, then the quote row (the order the first draft had reversed, which deadlocked two simultaneous accepts; `FOR NO KEY UPDATE` does not block a contractor's bid INSERT, whose foreign-key check takes KEY SHARE on the claim); the call is refused `42501` when another bid on the claim is live (item 4a); any other bid still `selected` and active is set to `declined` before the new one is selected (item 4b); and a repeated accept of the bid that is already the live selected one returns without writing (proof X2, X2b: before, it rewound a signed claim to `awarded` and rewrote `selected_bid_amount`). The first award on a claim is unchanged (proof L8); a stranger is still refused as today (X3). Proof X1c is the closes-on case: the losing $12,000 bid via `rpc accept_bid` beside the $9,000 winner, accepted today and refused after, with `commission=null` on completion (X1d). W3 is the switch case (switch, then award another bid: accepted, one selected bid); RB2 the rescind case (rescind, re-bid, award: accepted); RB3 the control (no rescind: refused).

Objects: one function added (`public.quotes_platform_fee_for(uuid, uuid)`, `STABLE SECURITY DEFINER`, EXECUTE for `authenticated` and `service_role` only), one index added (`quotes_one_selected_bid_per_claim`), three functions replaced (`quotes_guard_homeowner_columns()`, `apply_referral_commission()`, `accept_bid()`; EXECUTE grants on `accept_bid` are unchanged by `CREATE OR REPLACE`). No trigger, table, policy or data change. The lookup function is needed because `platform_fee_config` has one policy, `Admin can manage fee config` (`is_admin_email()`), so the guard, which runs as the caller, cannot read it.

## Departures from the ruling's text, each forced by what the scan found
- The ruling lists `fee_accepted_at` among the refused columns. Both bid forms send it on every INSERT and every change-bid save, so it is on the contractor's allow-list (refusing it would break both forms). It is refused for the claim owner (proof C3).
- The ruling names the homeowner's "signature stamps". The contractor also stamps `contractor_signed_at` from `contract-signing.html`, so that column is on the contractor's allow-list.
- "The config row the bid form reads": the forms cannot read it (finding 1). The lookup is the one both forms and `process-auto-bids` are written to make, with the contractor's state taken from `contractors.address_state`, as `process-auto-bids` does.

## Findings (not changed by this draft)
1. **The bid forms do not read the fee config today.** `platform_fee_config` is admin-only under RLS, so a contractor's SELECT returns 0 rows (proof line CFG), and the HTML form filters on `currentContractor.state`, a column `contractors` does not have. Both forms fall back to a hardcoded 5.0, which equals the configured 5.00. If the config row is ever changed, this draft stores the configured rate while the form still shows 5%. The form's read has to be fixed before the rate is changed (D-214: the contractor accepts the fee the platform displays). **Standing condition (CEO 6050104316, legal read 6050041234): `platform_fee_config` is not edited, by the admin fee page or any other route, until both bid forms read the server's rate and display it.** No lookup reads `effective_date`, so a future-dated row would also take effect at once (review 6050036561 N1).
2. **Bid renewal from the forms cannot succeed today.** The renewal payload sends `renewals_count`, which is not a column of `quotes` (49 columns, information_schema), and `bid_status = 'submitted'`, which `quotes_bid_status_check` does not allow (`active`, `expired`, `superseded`, `cancelled`). The allow-list refuses `bid_status`, `expired_at` and `expires_at` for the contractor, as the ruling says; when renewal is repaired it should go through `service_role`.
3. The admin fee page saves trades capitalised (`Roofing`) while every lookup compares lower case (`roofing`), and no lookup reads `effective_date`. With one all-states, all-trades row neither matters today.
4. `switch-contractor` writes `quotes.status = 'cancelled'`, which `quotes_status_check` does not allow (`draft`, `submitted`, `selected`, `declined`, `expired`); the function treats the error as non-fatal, so the switched-away bid stays `selected` (proof W1, W2). `rescind-bid` writes `bid_status = 'rescinded'`, which `quotes_bid_status_check` does not allow (proof RB1). Neither is changed in this PR; item 4 is written so that neither strands a claim.
5. `accept_bid()` still awards a bid that is dead: with `status = 'expired'`, `bid_status` cancelled or expired, or `status = 'declined'`, the call is accepted (re-review item 4; unchanged by this draft, same on today's schema). One line in the ownership SELECT, `AND q.bid_status = 'active' AND q.status IN ('submitted','draft','selected')`, would close it; left for a separate ruling because it changes which bids a homeowner may award.

## Residuals this draft does not close
- **R1 (measured, proof lines R1):** the claim owner can still decline the selected bid, select another and repoint `claims.selected_contractor_id` from the browser, which is a re-award outside `switch-contractor`. The commission then follows the re-awarded bid. Closing it means the owner can no longer un-select a bid from the browser, a product rule nobody has decided.
- **W4 (measured), the React award shape.** `react-app/app/(homeowner)/bids/actions.ts` repoints `claims` first, then selects the quote. With item 4, once the claim names the new contractor the old winner is no longer live, so the second write succeeds and the old winner is set to `declined`: a re-award by the claim owner without `switch-contractor` and without its refund step. The browser could already repoint `claims` (R1); what changes is that the previous head refused the second write and left the claim naming a contractor whose bid was not selected (a half-write), and this head completes it. The quotes table cannot tell this from the award that follows a switch (both: the old bid selected, the claim pointing elsewhere or nowhere). Closing it takes a change to the React award (call `accept_bid`) or a guard on `claims.selected_contractor_id`; neither is in this PR.
- **A direct select with nothing awarded.** A claim owner selecting a bid by UPDATE while another bid is `selected` but the claim does not point at it (for example, two bids set one after the other on a claim with no selected contractor) sets the earlier one to `declined` instead of being refused; one selected bid remains (proof E5).
- **Race window.** Two simultaneous direct UPDATEs or a direct UPDATE beside `accept_bid()` are closed by the index: the loser fails `23505` (`duplicate key value violates unique constraint "quotes_one_selected_bid_per_claim"`), a Postgres sentence that the React award (`winErr.message`) would show as is; the HTML pages show their generic error (two-session proof C2, C3).
- **Notes editing after selection (D-381)** holds in the database (proof S8) but not through the pages for a bid with a custom warranty: both forms stamp `value_adds.warranty_admin_review.flagged_at` on every save (`contractor-bid-form.html` L5470-5477, `react-app/app/contractor/bid/[claimId]/utils.ts` L491-500), so a notes-only save changes `value_adds` and is refused once gh2564 is applied, and gh2564 precondition 2 removes "Change Bid" on a selected bid. A point for the product owner (re-review item 8).
- A browser-chosen `created_at` on INSERT, and `fee_accepted_at` being the browser's clock.

## Pre-flight SELECT for the index (must return 0 rows before apply)
The index cannot be built over a claim that already has two selected, active bids, and the migration's first statement is a `DO` block that raises (nothing is applied) if one exists. I cannot query production. **Assumption, from the read recorded above ("Claims with two selected bids: 0", 2026-10-08, 8 quote rows):** existing data has at most one selected, active bid per claim. A claim that went through `switch-contractor` and was awarded again since that read would break it (the old bid stays `selected`). Run this at apply time, as a SELECT:
```sql
SELECT claim_id, count(*) AS selected_active_bids, array_agg(id ORDER BY created_at) AS quote_ids
  FROM public.quotes
 WHERE status = 'selected' AND bid_status = 'active'
 GROUP BY claim_id
HAVING count(*) > 1;
```
If it returns a row, stop and rule on each (which bid stands, the other is set to `declined` by hand); do not edit the migration to skip it.
